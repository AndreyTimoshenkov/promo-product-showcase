# Товары промо-акции: таблица с фильтрами

Фрагмент фронтенда из реального проекта (Angular 20, NgRx Signals, RxJS) в обезличенном виде.
В исходнике это каталог расширений, которые подключаются в чатах: страница расширения со списком,
поиском, тегами, сортировкой и пагинацией. Предметную область заменил на «товары промо-акции».
Устройство стора, транспорт и логика фильтров взяты из оригинала, компонент упрощён
(подробности в конце).

Настоящего бэкенда у фрагмента нет. Чтобы экран можно было открыть, я добавил мок-данные:
HTTP-перехватчик в `demo/` эмулирует обе ручки — фильтрует, сортирует и режет на страницы
сгенерированные товары, как это делал бы сервер.

## Что делает

Экран `/promo-campaigns/:campaignId/products` показывает товары акции постранично: артикул, цены,
скидку и остаток. Фильтры:

- поиск по названию или артикулу с debounce;
- сортировка;
- «только в наличии»;
- теги в трёх состояниях: выбран, исключён, не учитывается. У каждого тега счётчик товаров
  по текущему срезу фильтров.

**Что попадает в адрес.** Страница и теги хранятся в query-параметрах, поэтому ссылка воспроизводит
их. Поиск, сортировка и флаг наличия локальны для экрана и в ссылку не попадают: по ссылке
они откроются в значениях по умолчанию.

## Запуск

Нужен Node.js 20.19+, 22.12+ или 24+ (требование Angular 20; проверено на 22.16) и npm.

```bash
npm ci              # зависимости ровно по package-lock.json
npm start           # демо-стенд: открыть http://localhost:4300
```

Остальные команды:

```bash
npm test            # Jest: 54 теста
npm run typecheck   # ngc со strictTemplates
npm run build       # сборка демо-стенда в dist/demo
```

## Проверка

Код для оценки — `src/`. Тесты запускаются сами по себе: Jest гоняет их в Node с jsdom и `TestBed`,
HTTP в каждом спеке подменён, поэтому ни приложение, ни бэкенд не нужны.

**Демо-стенд** (`demo/`) — не часть фичи, а минимальный хост, чтобы экран можно было открыть
в браузере. Бэкенда у него нет: обе ручки отвечает HTTP-перехватчик `demo/mock-backend.interceptor.ts`
со сгенерированными товарами и задержкой ~0,6 с, чтобы были видны скелетоны и полупрозрачная прошлая
страница. Ссылки в шапке открывают три акции:

- «Летняя распродажа» — 320 товаров;
- «Снова в школу» — 140 товаров, теги приходят в обёртке `{ tags }`;
- «Акция с ошибкой бэкенда» — ручка товаров отвечает 500, видно состояние ошибки и «Повторить».

Хост собран ровно из того, что фиче нужно от приложения, и работает без zone.js:

- `provideHttpClient()`. Пути ручек относительные (`/promo-campaigns/...`), базовый адрес API
  подставляет интерсептор или прокси хоста;
- `provideRouter(PROMO_PRODUCTS_ROUTES, withComponentInputBinding())`: без привязки
  параметров `campaignId` не попадёт во input компонента;
- `registerLocaleData(localeRu)` из `@angular/common/locales/ru` для `CurrencyPipe` с локалью `ru`.

## Состав

```

  data-access/
    promo-products-backend.service.ts      HTTP-транспорт: две ручки, без собственной логики
    promo-products-backend.utils.ts        чистые функции: query-параметры, маппинг DTO → модель
    promo-products-backend.utils.spec.ts   тесты утилит транспорта без TestBed
    promo-products.model.ts                форма состояния стора и начальное значение
    promo-products.store.ts                NgRx SignalStore: загрузка выдачи и тегов
    promo-products.store.spec.ts           тесты стора
    promo-products-backend.service.spec.ts тесты связки с HTTP (HttpTestingController)
  feature/
    promo-products.component.ts|html|scss  OnPush-компонент: Reactive Forms, таблица, пагинация
    promo-products.component.spec.ts       тесты компонента через RouterTestingHarness
    promo-products.const.ts                размер страницы, debounce, варианты сортировки
    promo-products.interface.ts            view-модели: строка таблицы, тег со статусом
    promo-products.utils.ts                чистые функции: страница, строка таблицы, статусы тегов
    promo-products.utils.spec.ts           тесты утилит без TestBed
    promo-products.routes.ts               ленивый маршрут (loadComponent)
demo/                                      демо-хост и мок-бэкенд, не часть фичи
```

Данные идут в одну сторону: **компонент → стор → сервис → HTTP**, а в обратную сторону через сигналы.

Типы разложены по владельцу. Контракт API лежит в корне, потому что его используют и транспорт,
и стор, и компонент. Форма строки таблицы и подписи сортировок нужны только экрану, поэтому
они лежат в `feature/`. В компоненте осталась только связка: форма, сигналы, эффекты и навигация.
Суффикс файла говорит о его роли: `.interface`, `.enum`, `.const`, `.utils`, `.model`.

## Почему решения именно такие

**Стор на уровне компонента.** У `PromoProductsStore` нет `providedIn: 'root'`. Компонент
объявляет его в `providers` и получает свой инстанс. Состояние живёт и умирает вместе с экраном,
поэтому две выдачи одной акции (например, превью и полная таблица) не перетирают друг другу
страницу и фильтры. Изменения состояния идут через `updateState` с именем действия, поэтому
в Redux DevTools видна вся история загрузок.

**RxJS там, где важен порядок ответов.** `load` и `loadTags` сделаны через `rxMethod`
с цепочкой `filter → switchMap → catchError`:

- `filter` по ключу запроса отсекает повтор той же страницы, даже если эффект компонента
  сработал ещё раз. Ключ — структурная сериализация параметров, поэтому тег с запятой внутри
  не совпадёт с парой тегов;
- `switchMap` отписывается от устаревшего запроса, когда пользователь быстро листает или печатает,
  поэтому в стор попадает только ответ на последний;
- ошибка гасится внутри `switchMap`, иначе первая же ошибка завершила бы весь поток загрузки.
  После ошибки тот же запрос снова проходит фильтр, и «Повторить» — это обычный `load`.

**Два флага загрузки.** `loaded` сбрасывается при каждом запросе. `hasCompletedRequest` живёт
до смены акции. По второму флагу таблица рисует полный скелетон только при первой загрузке.
При смене страницы прошлые строки остаются полупрозрачными, и таблица не прыгает по высоте.

**«Размер неизвестен» и «выдача пуста» — разные состояния.** Стор хранит размер выдачи вместе
со срезом, к которому он относится: акцией, поиском, тегами и флагом наличия. Для любого другого
среза размер неизвестен, и номер страницы из адреса уходит в запрос как есть: ссылка на пятую
страницу сразу грузит пятую, даже если до этого была открыта выдача поуже. Когда размер среза
известен, номер ограничивается последней страницей: ссылка на двенадцатую при трёх страницах
загрузит третью и поправит адрес.

**Смена фильтра сбрасывает страницу без лишнего запроса.** `linkedSignal` запоминает, при каких
локальных фильтрах в адресе появилась текущая страница. Когда фильтры меняются, запрос сразу
уходит за первой страницей, а адрес догоняет его с `replaceUrl`.

**Фильтрация и сортировка на сервере.** Клиент держит в памяти одну страницу (50 строк).
Поэтому таблица не тормозит на каталоге в десятки тысяч позиций, и виртуальный скролл здесь
не нужен. Для бесконечной ленты его можно добавить через `cdk-virtual-scroll-viewport`,
не меняя стор.

**Reactive Forms и сигналы.** Фильтры собраны в типизированную `FormGroup` через
`NonNullableFormBuilder`. Поиск проходит через `debounceTime`, и все `valueChanges` превращаются
в сигналы через `toSignal`; повторы отсеивает сам сигнал. Из сигналов `computed` собирает объект запроса.

**OnPush и lazy loading.** Компонент работает в `ChangeDetectionStrategy.OnPush` и читает
только сигналы. Маршрут подключён через `loadComponent`, поэтому компонент, стор и транспорт
попадают в отдельный чанк. Цены форматирует `CurrencyPipe` с локалью `ru`: приложение
регистрирует её через `registerLocaleData`.

**Теги с тремя состояниями доступны без цвета.** На экране «выбран» и «исключён» различаются
цветом и зачёркиванием, поэтому каждая кнопка несёт состояние ещё и скрытым текстом
(«Выпечка, исключён»), а подсказка над списком тегов объясняет порядок переключения.
`aria-pressed` здесь не подходит: он различает только два состояния.

**Транспорт без бизнес-логики.** Сервис только выбирает ручку. Сборка `HttpParams` без пустых
значений и маппинг DTO из snake_case в модель — чистые функции в `promo-products-backend.utils.ts`,
поэтому их крайние случаи проверяются без `TestBed`. Размер выдачи
и список тегов принимаются в обеих формах, которые отдаёт ручка.

## Что изменено относительно оригинала

- Переименованы сущности, эндпоинты и тексты. Убраны внутренние пути библиотек и брендовые флаги.
- В проекте экран собран на собственном UI-ките: поле поиска, select, пагинация, теги, скелетоны
  и заглушки — его компоненты со своими стилями и темами. Кит здесь убран целиком, вместо него
  нативные элементы и минимальный `promo-products.component.scss`. Поэтому разметку и стили стоит
  читать как заглушку под фрагмент, а не как пример вёрстки из продакшена.
- В проекте вёрстка на Tailwind CSS: утилиты в шаблонах, а `.scss` компонента — только для того,
  что утилитами не выразить. Из фрагмента Tailwind убран целиком: без сборки приложения его классы
  не превратились бы в CSS, поэтому раскладка и состояния описаны обычным SCSS.
- Тексты интерфейса написаны прямо в шаблоне. В оригинале они идут через i18n-ключи
  Transloco; здесь библиотеку не тянул, чтобы фрагмент запускался сам по себе.
- Компонент упрощён. В оригинале карточная сетка с адаптивным размером страницы под
  брейкпоинты, ленивая панель тегов и общий тулбар каталога. Здесь вместо этого нативная
  таблица, фиксированный размер страницы и минимальные стили.
